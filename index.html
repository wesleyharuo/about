Fraud detection · machine learning

CardGuard

A credit card fraud detection system rebuilt from scratch as software, not a notebook. The question behind it: how do you keep a fraud model trustworthy after it's deployed, when fraud patterns and customer behaviour keep shifting?

View repository
config›data›features›models›evaluation›drift monitor›CLI inference

Outcome. A fraud model packaged as software that can be trained, evaluated and run the same way anywhere, and that warns when incoming data drifts away from what it was trained on.

Why these choices

  • Fraud is rare, so accuracy is misleading; the evaluation uses ROC-AUC, PR-AUC and confusion matrices
  • PR-AUC shows how well the model finds fraud without flooding analysts with false alarms
  • PSI and the KS statistic detect when incoming data drifts away from training data
  • MLflow tracks every experiment; Docker makes runs reproducible

Connection to my work

The same instinct as reconciliation: don't trust a result just because it was right once. Canada-specific configuration notes PIPEDA and PCI DSS considerations for handling card data.

How it was built, step by step
  1. Frame the problem. Fraud detection is an imbalanced binary classification: frauds are a tiny share of transactions, so the metrics and sampling have to reflect that from the start.
  2. Configure, don't hard-code. A configuration file defines data paths, features, model choice and thresholds, so each experiment is reproducible and comparable.
  3. Data layer. Loads the transactions and splits them into training and evaluation sets, isolated from the rest of the code.
  4. Feature layer. Transformations live in one module, so exactly the same logic runs in training and in inference.
  5. Model layer. LightGBM and XGBoost gradient boosting, with class weighting or undersampling to handle imbalance, and Optuna searching the hyperparameter space.
  6. Evaluation layer. ROC-AUC, PR-AUC and confusion matrices, with every run and its parameters logged in MLflow.
  7. Drift monitoring. PSI and the KS statistic compare new data against the training baseline to show when the model is seeing a different world.
  8. Packaging. Command-line tools for train, evaluate and infer, inside a Docker image so it runs the same everywhere.
Methodology notes
Why PR-AUC
When 99% of transactions are legitimate, a model that never flags fraud is 99% accurate and useless. Precision-recall shows the real trade-off: how much fraud is caught versus how many false alarms analysts receive.
PSI
Splits a variable into bins and compares the share of records in each bin between training and new data: Σ (new% − base%) × ln(new% / base%). A common rule of thumb reads under 0.1 as stable and above 0.25 as a significant shift.
KS statistic
The largest gap between two cumulative distributions. Used here to detect whether a feature's distribution has moved away from what the model was trained on.
Weighting vs undersampling
Weighting keeps all data but makes fraud errors cost more; undersampling removes legitimate records to balance classes. Supporting both lets the evaluation decide.
Optuna
Searches hyperparameters by learning from previous trials instead of testing every combination, which keeps tuning fast and documented.
Python · pandas · NumPy · scikit-learn · LightGBM · XGBoost · Optuna · MLflow · Docker
Insurance · document AI · full stack

KW Risk

A platform that streamlines insurance claims processing: it reads claim documents, classifies them, scores its own confidence and flags claims that look suspicious. It revisits, with modern tools, the duplicate-claim detection I did in SQL for a health plan in Brazil.

View repository
claim upload›OCR›NLP triage›rules engine+ML anomaly›confidence score›approve or review

Outcome. Clear claims are approved automatically, uncertain ones go to a human reviewer, and a live dashboard shows how much of the work is automated.

Why these choices

  • A rules engine catches known fraud patterns that are easy to explain
  • ML anomaly detection catches the unusual cases rules miss
  • Confidence scoring decides what can be automated and what needs a person

Connection to my work

It's the same design principle I apply to LLM invoice extraction: automation handles the clear cases, and anything uncertain goes to a human instead of passing silently.

How it was built, step by step
  1. Upload. The user submits claim documents through the React interface.
  2. Receive. The FastAPI backend accepts the files through its API and starts processing.
  3. Read. OCR converts scanned documents and images into machine-readable text.
  4. Understand. NLP classifies the document and extracts the information the claim depends on.
  5. Check known patterns. A rule-based engine tests the claim against explicit fraud rules.
  6. Check the unusual. ML anomaly detection scores how far the claim sits from normal behaviour.
  7. Decide who decides. A confidence score routes clear cases to automated approval and uncertain ones to a human reviewer.
  8. Measure. A real-time dashboard tracks how much is automated and how approvals evolve.
Methodology notes
Hybrid detection
Rules are transparent and easy to audit but only catch what someone already thought of. Anomaly detection finds new patterns but is harder to explain. Using both covers each one's blind spot.
Human in the loop
The confidence threshold is a business decision, not only a technical one: it sets how much risk the insurer accepts in exchange for speed.
Separated deployment
The frontend runs on Vercel and the API on Uvicorn, so each can be updated and scaled independently.
React · Vite · Tailwind CSS · FastAPI · Uvicorn · Python · OCR · NLP · Vercel

AI Fraud Detection Canada

An end-to-end fraud detection design for Canadian banks, credit unions and fintechs, covering the full path from data ingestion to a decision, with monitoring and bilingual support.

View repository
ingestion›feature engineering›model ensemble›decision›monitoring and alerts

Outcome. A design that ends in a traceable decision rather than a bare score, fits FINTRAC and PIPEDA obligations, and serves users in English and French.

Why these choices

  • Canadian institutions work under FINTRAC reporting and PIPEDA privacy rules, so those considerations are built into the design
  • Bilingual support reflects how Canadian financial services actually operate

Connection to my work

It applies my experience with regulated data, clinical in Brazil and financial in both countries, to the Canadian context I work in now.

How it was built, step by step
  1. Map the context. Start from how Canadian banks, credit unions and fintechs operate, including reporting and privacy obligations.
  2. Ingest. Transaction data enters through a dedicated ingestion stage.
  3. Engineer features. Raw transactions become the signals the models learn from.
  4. Score. Neural networks and ensemble methods produce a fraud assessment.
  5. Decide. The pipeline ends in a decision output, not just a score.
  6. Watch. A monitoring and alerting stack observes the system after deployment.
  7. Serve both languages. English and French support, as Canadian financial services require.
  8. Separate concerns. Each stage runs as its own microservice so it can change without breaking the others.
Methodology notes
Ensembles
Combining different models reduces the chance that one model's weakness becomes the system's weakness, a useful property when errors cost money.
FINTRAC
Canada's financial intelligence unit. Institutions must report certain transactions, so a fraud system has to support traceable decisions.
PIPEDA
Canada's private-sector privacy law. It shapes what personal data is collected, how it's used and how long it's kept.

Process Improvement Analytics Platform

A Streamlit platform with three interactive dashboards for retail sales, supply chain and customer support, fed by an automated pipeline where every stage is visible.

View repository
raw data›clean›validate›aggregate›retail · supply chain · support dashboards

Outcome. Three dashboards that non-technical users can explore without installing anything, all fed by one pipeline where bad records stop at validation instead of reaching a chart.

Why these choices

  • Validation is its own stage, so bad data stops before it reaches a chart
  • Streamlit lets non-technical users interact without installing anything

Connection to my work

It's the same shape as the Power Query workflows I built at Humberview: validation inside the flow, not a check at the end.

How it was built, step by step
  1. Define the questions for each area: sales performance, delivery efficiency and support quality.
  2. Load the operational data for the three domains with pandas and SQL.
  3. Clean. Standardize formats and deal with missing or invalid values before anything else runs.
  4. Validate. A dedicated stage checks the data against rules, so bad records stop here instead of reaching a chart.
  5. Aggregate into KPIs: revenue and volume, carrier efficiency and delivery times, resolution time and satisfaction.
  6. Visualize with Plotly inside three Streamlit dashboards that non-technical users can explore.
Methodology notes
Validation as a stage
Separating validation from cleaning makes failures visible and explainable. It's the same principle as reconciling after every load in a migration.
One pipeline, three domains
Retail, supply chain and support share the same clean, validate and aggregate pattern, which shows the design is reusable rather than one-off.

July 2025Practitioner essay

The Escalating Security Challenge of AI-Generated Code

What I kept running into when reviewing code suggested by AI assistants, and the review process I recommend before any of it reaches production.

What I found

  • SQL queries built by concatenating user input without validation
  • Authentication that doesn't properly check credentials, and sessions that stay open too long
  • Suggestions to install packages that don't exist or aren't maintained

Why it happens

  • Models learn from public code that includes insecure patterns
  • They replicate patterns without understanding the security context
  • Developers accept suggestions because they look authoritative

What I recommend

  • Mandatory human review
  • SAST, DAST and SCA across the lifecycle
  • Clear standards for validation and dependencies
  • Ongoing team education and dependency monitoring
2026Independent thesis

Generative Code Security Engineering

The essay's intuition, formalized. The central argument: the real danger of AI-generated code isn't one flawed function, it's how a flaw spreads through dependencies into distant parts of a system. The thesis proposes a framework, GCVP, to classify, measure and reduce that spread.

Classify

  • A taxonomy of seven ways AI introduces vulnerabilities, from reproducing insecure training patterns to drift after model updates
  • Seven impact classes, from self-contained flaws to supply chain amplification
  • A threat model for prompt-based attacks, including indirect injection through data

Measure

  • A dependency graph where each module carries a trust level and each connection a coupling strength
  • VPI: the probability a flaw travels from one module to another
  • SLES: a single exposure score for the whole system, weighted by how critical each module is

Reduce

  • A seven-stage secure generation pipeline, SAGP
  • Controls scale with risk: the less trusted the code's origin, the more stages are mandatory
  • A compliance score to measure how fully the pipeline is applied

June 2026Research article

Ghost Jobs, Broken Code, and the AI Security Crisis Inside Canada's Public Sector

A synthesis of public Canadian sources connecting three problems: job postings that lead to no hire, public servants using unapproved AI tools, and fake job ads used by foreign intelligence services to recruit people with access to sensitive information.

24.9–43.2%Ghost job rates reported across Canadian platforms
244 of ~400AI sites used by Ontario public servants rated unsafe
3%Of Ontario public servants completed AI safety training
42,755Confirmed CRA cases of unauthorized taxpayer data use

How it was done

  • Compiled findings from the Ontario Auditor General, the Privacy Commissioner, the Five Eyes joint bulletin and labour market studies
  • Organized them into ghost jobs, AI misuse, breaches, prompt injection and espionage

Key argument

  • Technology is being adopted faster than the knowledge needed to use it safely
  • The same platforms that host ghost jobs are also used for intelligence recruitment

Practical guidance

  • Use only approved AI tools; never paste protected data into public ones
  • Review public code and prompt templates before using them
  • Treat AI-generated text as a first draft that needs human review

How I work

The report is the last step, not the first.

When a number doesn't agree, I trace it back to where the record broke instead of adjusting the output. This is the sequence I follow, and three procedures I use in practice.

  1. Requirements

    What decision will this number support, and who needs to trust it?

  2. Data model

    Entities, keys and the chart of accounts before any query is written.

  3. SQL and ingestion

    Extraction, cleaning and loading with checks at each stage.

  4. Reconciliation

    Every total tied back to the books or the system of record.

  5. Automation

    Repeatable jobs replace manual re-keying, with validation built in.

  6. Reporting

    Dashboards and commentary built on one validated dataset.

Used at NextLens Data

  2. Extract fields with an LLM using a structured prompt.
  3. Validate every value against the chart of accounts and business rules.

Accepting AI-generated code

From my 2025 essay
  1. Treat the suggestion as a draft, not an answer.
  2. Review it manually, ideally with a peer.
  3. Run automated scans: SAST, DAST and dependency checks (SCA).
  4. Verify every package exists and is maintained, to avoid slopsquatting.
  5. Deploy to staging first, then monitor in production.
